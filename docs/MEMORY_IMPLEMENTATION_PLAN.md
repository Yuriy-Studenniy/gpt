## 2. Целевая архитектура без лишних сервисов

Для первого рабочего варианта предлагается один внешний Companion Runtime — один процесс, внутри которого находятся:

1. адаптер выбранного LLM-провайдера;
2. API памяти и сборщик контекста;
3. долговременное хранилище;
4. очередь фоновой консолидации;
5. интерфейс обмена событиями с игрой.

Не дробить MVP на микросервисы. Хранилище, retrieval и LLM-клиент — модули одного runtime с ясными интерфейсами.

### Внутри игры

Тонкий Lua adapter для уникального Story ID `gpt_companion_main` должен:

- передавать в runtime только события реального диалога и заранее выбранные значимые игровые события;
- получать готовый ответ/результат через подтверждённый транспорт;
- иметь request ID, timeout, отмену/устаревание ответа и защиту от повторной доставки события;
- не запускать сетевые запросы, базу данных, embedding-модель или LLM в `actor_binder:update()`, `motivator_binder:update()` или NPC update logic;
- не менять ванильный путь обычных NPC;
- не расширять бинарный пакет `sim_squad_scripted` без отдельного аудита совместимости сохранений.

**Транспорт между оригинальным X-Ray и внешним runtime пока не выбран.** Нельзя предполагать наличие HTTP/socket API в retail Lua. Сначала нужен отдельный технический spike на реальной CoP 1.6.02: какие способы IPC действительно доступны и безопасны. Если прямой транспорт требует DLL/launcher-компонент, оценить это отдельно, а не имитировать несуществующий Lua API.

### Внешний Companion Runtime

Runtime отвечает за приём событий, долговременную запись, retrieval, сборку компактного prompt, вызов модели и возврат ответа. При недоступности memory retrieval он использует недавний контекст/hot cache и не блокируется бесконечно.

## 3. Минимальный контракт памяти

Первую схему следует держать небольшой и версионируемой:

### `conversations`

- `conversation_id` — устойчивый ID разговора;
- `scope_id` — профиль/кампания/ветка истории;
- `created_at`, `updated_at`;
- `summary` — актуальная краткая сводка;
- `summary_from_seq`, `summary_to_seq` — диапазон реплик, покрытый сводкой;
- `version` — версия состояния для optimistic update.

### `messages`

- `message_id`, `conversation_id`, `sequence`;
- `speaker`: player, companion, external_assistant, npc, engine;
- `content`, `created_at`, `source`;
- `metadata` — компактные структурированные метаданные;
- уникальность `(conversation_id, sequence)` и идемпотентность по `message_id`.

Исходные сообщения хранятся append-only: исправление/уточнение добавляет новую запись или связь, а не стирает историю.

### `memory_items`

- `memory_id`, `scope_id`, `kind`;
- `subject_key` / сущность, к которой относится воспоминание;
- `content`, `source_message_id` или ссылка на игровой event;
- `perspective`: shared или companion_private;
- `confidence`, `importance`, `status`;
- `created_at`, `last_confirmed_at`, `supersedes_id`.

Договорённости, обещания и открытые вопросы могут быть типами `memory_items` с явным жизненным статусом; отдельные таблицы добавлять только если измерения/запросы покажут реальную необходимость.

### `retrieval_index`

Индекс не является источником истины. Он может перестраиваться из журнала и memory items. Точный поиск по ключам/сущностям и обычные индексы обязательны; полнотекстовый индекс подключается при доступности и проверке используемой SQLite-сборки.

## 4. Простое хранилище для MVP

Основной кандидат — **одна локальная SQLite база** во внешнем runtime:

- транзакционная запись сообщений и памяти;
- обычные B-tree индексы по conversation, sequence, entity, kind, status и времени;
- WAL для одновременного чтения и записи, если выбранная сборка/режим это корректно поддерживает;
- FTS5 как первый полнотекстовый индекс, только после проверки его наличия в целевой сборке SQLite;
- никаких отдельных vector DB и embedding-моделей на первом этапе.

Если FTS5 недоступен, начать с обычных индексов и простого лексического поиска. Семантический/vector retrieval добавлять только когда тестовый набор покажет конкретные провалы точного/полнотекстового поиска. Сначала получить базовую скорость и качество простого решения.

## 5. Быстрый путь ответа

Критический путь одного ответа:

1. принять новую реплику и быстро записать её в журнал;
2. получить из hot cache короткую сводку и недавние сообщения;
3. дешёвыми индексированными запросами найти активные договорённости и небольшое число релевантных воспоминаний;
4. собрать prompt в установленном token budget;
5. вызвать основную LLM и вернуть ответ;
6. записать ответ в журнал.

Консолидация старых сообщений и обновление долгосрочных сводок работают в отдельной очереди. Если обработчик не успел, исходные реплики уже сохранены и доступны для retrieval; ответ не ожидает полного rebuild.

На первом этапе retrieval не делает отдельный LLM-вызов. Если провайдер поддерживает structured output/tool calls, основная генерация может возвращать компактный memory patch вместе с ответом. В противном случае долговременная консолидация запускается пакетно по порогу/границе беседы, а не отдельным запросом на каждую реплику.

### Контекст для модели

Порядок приоритета:
1. неизменяемые инструкции/персона и актуальное состояние;
2. активная тема и нерешённые договорённости;
3. последние реплики;
4. текущая сводка беседы;
5. top-K релевантных долговременных воспоминаний с источниками.

Численные token/latency бюджеты не назначать до baseline. Контекст должен оставаться ограниченным при росте всей базы.

- уникальность `(conversation_id, sequence)` и идемпотентность по `message_id`.

Исходные сообщения хранятся append-only: исправление/уточнение добавляет новую запись или связь, а не стирает историю.

### `memory_items`

- `memory_id`, `scope_id`, `kind`;
- `subject_key` / сущность, к которой относится воспоминание;
- `content`, `source_message_id` или ссылка на игровой event;
- `perspective`: shared или companion_private;
- `confidence`, `importance`, `status`;
- `created_at`, `last_confirmed_at`, `supersedes_id`.

Договорённости, обещания и открытые вопросы могут быть типами `memory_items` с явным жизненным статусом; отдельные таблицы добавлять только если измерения/запросы покажут реальную необходимость.

### `retrieval_index`

Индекс не является источником истины. Он может перестраиваться из журнала и memory items. Точный поиск по ключам/сущностям и обычные индексы обязательны; полнотекстовый индекс подключается при доступности и проверке используемой SQLite-сборки.

## 4. Простое хранилище для MVP

Основной кандидат — **одна локальная SQLite база** во внешнем runtime:

- транзакционная запись сообщений и памяти;
- обычные B-tree индексы по conversation, sequence, entity, kind, status и времени;
- WAL для одновременного чтения и записи, если выбранная сборка/режим это корректно поддерживает;
- FTS5 как первый полнотекстовый индекс, только после проверки его наличия в целевой сборке SQLite;
- никаких отдельных vector DB и embedding-моделей на первом этапе.

Если FTS5 недоступен, начать с обычных индексов и простого лексического поиска. Семантический/vector retrieval добавлять только когда тестовый набор покажет конкретные провалы точного/полнотекстового поиска. Сначала получить базовую скорость и качество простого решения.

## 5. Быстрый путь ответа

Критический путь одного ответа:

1. принять новую реплику и быстро записать её в журнал;
2. получить из hot cache короткую сводку и недавние сообщения;
3. дешёвыми индексированными запросами найти активные договорённости и небольшое число релевантных воспоминаний;
4. собрать prompt в установленном token budget;
5. вызвать основную LLM и вернуть ответ;
6. записать ответ в журнал.

Консолидация старых сообщений и обновление долгосрочных сводок работают в отдельной очереди. Если обработчик не успел, исходные реплики уже сохранены и доступны для retrieval; ответ не ожидает полного rebuild.

На первом этапе retrieval не делает отдельный LLM-вызов. Если провайдер поддерживает structured output/tool calls, основная генерация может возвращать компактный memory patch вместе с ответом. В противном случае долговременная консолидация запускается пакетно по порогу/границе беседы, а не отдельным запросом на каждую реплику.

### Контекст для модели

Порядок приоритета:
1. неизменяемые инструкции/персона и актуальное состояние;
2. активная тема и нерешённые договорённости;
3. последние реплики;
4. текущая сводка беседы;
5. top-K релевантных долговременных воспоминаний с источниками.

Численные token/latency бюджеты не назначать до baseline. Контекст должен оставаться ограниченным при росте всей базы.

## 6. Порядок реализации

| Этап | Что делаем | Что должно работать перед переходом дальше |
|---|---|---|
| M0. Контракт и аудит | Схема событий, ID, области памяти, версия API, границы Lua/runtime; аудит текущих модулей | Контракт независим от модели; подтверждено, что текущий Lua-код не является LLM runtime |
, ответ из Lua через временный файл и rename | `IPC ROUND-TRIP OK` и маркеры Lua получены на оригинальном CoP 1.6.02; до этого транспорт остаётся кандидатом, не runtime-подтверждением |
| M2. Runtime + журнал | Один внешний Companion Runtime, локальное хранилище, append/read message API, идемпотентность | История точно записывается и восстанавливается после перезапуска |
| M3. Быстрый retrieval | Hot cache, recent turns, активные договорённости, точный/FTS поиск, token-budget | Контекст собирается без отдельного LLM-запроса и остаётся ограниченным |
| M4. Первый LLM vertical slice | Подключить одну модель через provider adapter и test harness; запрос/ответ, retrieval и source IDs | Настоящий длинный разговор использует сохранённую память; модель подключена рано, не дожидаясь всей личности/автономии |
| M5. Игровой диалоговый мост | Подключить проверенный IPC к уникальному companion; передача контекста и возврат ответа через отдельный диалоговый путь | Можно поговорить с NPC в CoP; timeout/retry не вмешиваются в actor/NPC update и обычные диалоги |
| M6. Консолидация | Сводки, извлечение событий/обещаний, дедупликация, противоречия, открытые темы | Старый разговор сжимается без потери важных фактов; фоновые задачи не тормозят ответ |
| M7. Личная память и Character Core | Собственная перспектива, эмоции, убеждения, отношения, цели | Персонаж отличает сказанное от собственного вывода и использует личный опыт |

M4 подключает модель через внешний test harness сразу после M2–M3, чтобы проверять память на настоящих разговорах, не дожидаясь полного игрового моста. M5 подключает этот уже работающий runtime к NPC после IPC spike. Ни один этап не требует сначала завершить весь Character Core или автономное поведение.

## 7. Проверки качества и производительности

Обязательный тестовый набор:
- точный recall имён, чисел, просьб и обещаний после длинной беседы;
- возврат к теме после нескольких новых разговоров;
- корректный статус незакрытого вопроса/обещания;
- исправление ошибочной записи без потери исходного источника;
- личная интерпретация companion не переписывает общий журнал;
- восстановление после остановки runtime и после save/load игры;
- p50/p95 задержки ответа с памятью/без памяти;
- дополнительная задержка retrieval, token count и размер hot context;
- поведение при медленной/недоступной БД и при незавершённой фоновой консолидации.

Оптимизацию нельзя оценить до получения baseline на реальной конфигурации пользователя. Сначала измерить, затем выставлять budgets. Не обменивать скорость на потерю важных фактов или наоборот.

## 8. Решения, которые пока нельзя принимать наугад

- конкретный IPC для retail X-Ray;
- точный формат campaign/save identity и поведение при загрузке старого сейва/ответвлении от копии сейва;
- физическое размещение внешнего runtime (отдельный процесс/уже существующее GUI приложение) — сначала проверить, есть ли пригодный текущий host за пределами этого репозитория;
- целевой провайдер и API модели;
- точные token/latency budgets после baseline.
