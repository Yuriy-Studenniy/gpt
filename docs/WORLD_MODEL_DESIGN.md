# Модель мира Зоны — проектирование AI Stalker Companion

Статус: проект архитектуры v0.1  
Дата: 2026-11-08  
Целевая среда: S.T.A.L.K.E.R.: Call of Pripyat 1.6.02, оригинальный X-Ray  
Основной репозиторий: https://github.com/Yuriy-Studenniy/gpt

> Документ задаёт контракт будущей подсистемы. Он не утверждает, что перечисленные API уже полностью проверены в runtime. До появления адаптеров и проверок это архитектурное описание, а не готовая игровая функция.

## 1. Назначение

Модель мира должна дать компаньону собственное, неполное и постепенно расширяющееся представление о Зоне: где находятся места, что там можно найти, кто там бывает, какие услуги доступны, какие угрозы и маршруты известны персонажу.

Модель мира не должна превращаться в копию внутреннего состояния X-Ray. Движок знает состояние симуляции, а компаньон знает только то, что:

- лично наблюдал;
- узнал от другого персонажа или из другого допустимого источника;
- вывел из уже имеющихся знаний.

Поэтому в системе существуют три строго раздельных слоя.

## 2. Три слоя данных

### 2.1. Каталог мира — что существует

Каталог описывает устойчивые сущности игры и их связи: уровни, Smart Terrain, именованные места, торговцев, техников, группы, объекты и потенциальные точки интереса.

Каталог — справочник для внутренней работы мода. Наличие сущности в каталоге **не означает**, что компаньон знает о ней.

Каталог может содержать:
- стабильный внутренний **entity_id**;
- тип сущности;
- родительскую сущность (например, Smart Terrain внутри уровня);
- привязку к идентификатору движка: имя уровня, имя Smart Terrain, Story ID или другой проверенный ключ;
- ключ локализации и статические классификационные теги;
- указание на источник определения сущности.

Каталог не должен хранить динамические факты вроде текущего здоровья NPC, содержимого инвентаря или текущей позиции online-объекта. Их источник — движок.

### 2.2. Состояние движка — что фактически происходит сейчас

Адаптер X-Ray получает текущее состояние по запросу или в момент события. Это слой объективных фактов, а не память персонажа.

В существующих исходниках уже используются следующие точки интеграции:
- **game_graph():vertex(...):level_id()** — получение ID уровня из game-graph vertex;
- **alife():level_name(level_id)** — имя уровня; **smart_terrain.script** использует эту связку при регистрации Smart Terrain;
- **sim_board** / **db.smart_terrain_by_id** — реестр Smart Terrain симуляции и online-объектов;
- **story_objects** и **get_story_object_id()** — поиск конкретного Story ID;
- **db.storage** — доступ к некоторым online-объектам и их данным.

Эти источники являются техническими точками интеграции, но не дают персонажу автоматического знания о найденных объектах.

Дополнительное уточнение по исходникам:
- В начале **sim_board.script** задана таблица **group_id_by_levels** с именами **zaton**, **pripyat**, **jupiter**, **labx8**, **jupiter_underground**. Числа 1–5 в этой таблице — внутренние ID группировки A-Life по уровням; это **не** числовые **game_graph level_id**. Их нельзя подставлять в API уровня.
- В **se_smart_terrain:on_before_register()** уровень Smart Terrain определяется именно через **game_graph():vertex(self.m_game_vertex_id):level_id()**, после чего имя берётся через **alife():level_name(...)**. Это подтверждает безопасный путь связи Smart Terrain с уровнем на уровне используемой игровой логики.
- **db.smart_terrain_by_id** и **sim_board.smarts** — runtime-реестры; их доступность и полноту в конкретных online/offline ситуациях нужно проверять отдельно. Их нельзя считать долговременным каталогом знаний персонажа.

Движковые ID и указатели на объекты нельзя считать долгосрочными ID знаний: online/offline переходы могут менять доступность Lua-обёртки. В сохранённом знании следует хранить стабильные строковые идентификаторы сущностей, а объект движка запрашивать заново при необходимости.

### 2.3. Знания компаньона — что известно персонажу

Это отдельный слой, который заполняется только событиями наблюдения, сообщениями и обоснованными выводами. Именно его в дальнейшем разрешено читать Character Core и внешнему агенту/LLM.

Принцип: **наличие сущности в каталоге не означает, что компаньон знает о ней.**

Каждое знание должно иметь происхождение и эпистемический статус. Минимальные поля утверждения:

| Поле | Назначение |
|---|---|
| claim_id | Уникальный ID утверждения |
| subject_id | О какой сущности идёт речь |
| predicate | Что именно утверждается: located_at, has_service, dangerous, controlled_by и т. п. |
| value | Значение утверждения |
| status | observed, reported, inferred |
| source_type | Наблюдение, разговор, событие, вывод |
| source_id | Кто/что стало источником, если применимо |
| confidence | Уверенность от 0 до 1 |
| created_at | Игровое время получения |
| last_confirmed_at | Игровое время последнего подтверждения, если оно было |

Нельзя незаметно перезаписывать противоречащие сведения. Несовместимые утверждения должны сосуществовать с разными источниками и уверенностью. Позже Character Core сможет выбирать, чему верить, и объяснять причину.

Устаревшее знание не становится автоматически ложным. Оно помечается как давно не подтверждавшееся; актуальность зависит от типа факта. Например, географическое положение места обычно стабильно, а наличие конкретного NPC или запас медикаментов может быстро измениться.

## 3. Сущности и устойчивые идентификаторы

Внутренние ID должны быть строковыми, namespaced и не зависеть от текущего online object ID.

Примеры формата (это схема, не утверждение о наличии конкретных сущностей в каталоге):
- **level:zaton**
- **smart:zaton:<smart_name>**
- **story:<story_id>**
- **poi:<level_id>:<stable_name>**
- **faction:<community_id>**
- **npc:<story_id>** — только для персонажей с устойчивым Story ID; для обычного NPC без него потребуется отдельная стратегия идентификации.

Одна и та же сущность не должна появляться под разными ID только потому, что движок переключил её online/offline.

Типы сущностей первой схемы:
- **level** — уровень/локация игры;
- **smart_terrain** — узел A-Life симуляции;
- **poi** — именованное место интереса;
- **npc** / **faction** — персонажи и группировки;
- **object** — конкретный объект мира;
- **route** — маршрут между известными местами (позднее).

Smart Terrain не следует автоматически считать полноценным нарративным местом: это прежде всего узел A-Life. Для вывода игроку/компаньону нужны отдельные метаданные и, возможно, привязка к понятному имени.

## 4. Первая версия: реестр уровней и мест (этап 2.1)

Первая итерация ограничивается географическим каркасом, а не всем миром сразу.

### 2.1.1. Справочник уровней
- перечислить игровые уровни, используемые CoP, в стабильном виде;
- связывать runtime level ID с внутренним entity_id;
- получить возможность сказать, на каком уровне находится спутник, не раскрывая ему автоматически остальные уровни и их содержимое.

### 2.1.2. Реестр Smart Terrain и именованных мест
- получать существующие Smart Terrain через штатные реестры симуляции;
- отделить технические smart-узлы от настоящих мест интереса;
- хранить родительский уровень и стабильный ключ движка;
- не сохранять координаты из случайной online-обёртки как единственный locator;
- для важных мест постепенно добавлять тип, название, описание, услуги и классификационные теги.

### 2.1.3. Открытие мест для компаньона
- при появлении персонажа текущий уровень и непосредственная обстановка могут быть зарегистрированы как исходный контекст;
- дальнейшее открытие мест должно идти через отдельные события наблюдения/рассказа;
- обнаружение одной базы не раскрывает все базы, тайники и объекты того же уровня;
- видимость, дистанция и условия наблюдения должны быть определены отдельно и проверены на целевом движке.

На этом шаге допустимо реализовать каталог и API чтения/записи знаний. Автоматический обход всех объектов мира с передачей результатов в слой знаний запрещён.

## 5. Предлагаемый контракт модуля gpt_world

Модуль — доменный сервис, а не схема NPC и не самостоятельный A-Life binder. Он не должен вызываться каждый кадр.

Первый кодовый артефакт: **gpt_world.script** (корень репозитория). В нём созданы:
- **gpt_world.get_catalog_entity(entity_id)** — возвращает копию записи статического каталога уровня или Smart Terrain;
- **gpt_world.get_catalog_levels()** — возвращает новый отсортированный массив записей уровней;
- **gpt_world.get_catalog_smart_terrains(level_entity_id)** — возвращает отсортированные Smart Terrain, с опциональной фильтрацией по ID уровня;
- **gpt_world.get_companion_location_snapshot()** — read-only адаптер фактов движка.

Каталог уровней содержит пять engine level names из mapping **group_id_by_levels** в **sim_board.script**: **zaton**, **jupiter**, **pripyat**, **labx8**, **jupiter_underground**. Их numeric values — T/S/G IDs, а не числовые Game Graph level ID; сами numeric Game Graph IDs здесь не зашиты.

Начальный каталог содержит **53 Smart Terrain/A-Life назначения** на четырёх основных игровых уровнях: Затон (25), Юпитер (18), Припять (9) и Лаборатория X-8 (1). Источники:
- значения из базовых секций **[start_position_zaton]**, **[start_position_jupiter]**, **[start_position_pripyat]**, **[start_position_labx8]** и их подвариантов в **simulation.ltx**; комментарий в этом файле прямо определяет правую часть записи как имя smart, к которому назначается squad;
- дополнительные именованные секции с **smart** в имени из **simulation_objects_props.ltx**, с level родителем, определённым по префиксу **zat_**, **jup_**, **pri_** или **lx8_**.

Исключены тестовые/сторонние start positions (**tgm_bug_test_***, **lain_selo**, **corr_***, ***_selo** и другие), закомментированные строки и не Smart Terrain назначения уровня Jupiter Underground (waypoint/path entries). Узлы `*_sim_N` помечаются как `simulation_node`, остальные записи — как `smart_terrain`. Это технический статический каталог A-Life адресов, не перечень нарративно известных мест и не знания компаньона. У некоторых секций нет удобного отображаемого названия/описания: его нельзя выдумывать, такие метаданные будут добавляться из подтверждённых источников позже.

Адаптер местоположения:
- ищет уникального компаньона через штатный **get_story_object_id("gpt_companion_main")**;
- получает A-Life server object через **alife():object(id)**;
- для online-компаньона предпочитает runtime wrapper из **db.storage[id].object**, а для offline использует server-side A-Life object;
- получает game vertex, затем **game_graph():vertex(...):level_id()** и имя через **alife():level_name(...)**;
- возвращает стабильные строковые IDs уровня и назначенного Smart Terrain, а также online/offline признак, если соответствующие данные доступны;
- возвращает **snapshot, nil** либо **nil, error_code**, не подставляя выдуманные значения.

### Lazy loading и точка интеграции

Самостоятельный модуль загружается не через **modules.script**. Этот файл регистрирует NPC-схемы, для которых **xr_logic.activate_by_section()** ожидает функцию **set_scheme()**; использовать этот путь для доменного сервиса было бы архитектурной ошибкой.

В X-Ray 1.6.02-based engine source подтверждён другой механизм:
- **CScriptEngine::setup_auto_load()** устанавливает __index metatable на глобальную таблицу **_G**;
- при обращении к отсутствующему глобальному имени **CScriptEngine::auto_load()** вызывает **process_file_if_exists(name, false)**;
- загрузчик ищет файл **name.script** в **$game_scripts$** и создаёт namespace с таким именем.

Источник для статической сверки: [script_engine.cpp — X-Ray 1.6.02 engine source](https://github.com/VideogameSources/STALKER-Call-of-Pripyat/blob/xd_dev/src/xrScriptEngine/script_engine.cpp), функции **auto_load**, **setup_auto_load**, **process_file_if_exists**. Оригинальная retail-сборка CoP в этой среде не запускалась, поэтому окончательное подтверждение доступности механизма в целевом executable остаётся runtime-проверкой.

В **bind_stalker.script** World Model lazy-load probe выполняется независимо от A-Life spawn/squad setup. После появления A-Life ID компаньона вызывается **gpt_companion_log_world_snapshot(companion_id)** — даже если регистрация squad ещё требует повторной попытки. Snapshot API принимает необязательный числовой **companion_alife_id**: при передаче использует уже известный ID через **alife():object(id)**, без зависимости от своевременного обновления Story ID registry; без аргумента сохраняется lookup по **gpt_companion_main**. Полученные level name, online/offline и Smart Terrain (если назначен) выводятся отдельными retail-visible диагностическими маркерами. Ошибки snapshot защищены pcall и не должны отменять создание компаньона или менять поведение NPC.

Проверки разделены на два независимых этапа и запускаются не из `actor_binder:update`. Core claims/observation self-test перенесён в `motivator_binder:update` самого компаньона: он запускается только для живого online-объекта с Story ID `gpt_companion_main`, после ещё 5 секунд работы его online binder. Core-тест использует временный `level:gpt_world_self_test` и не вызывает A-Life snapshot; исходная claim table и sequence ID восстанавливаются. Затем отдельный read-only вызов `get_companion_world_context(object_id)` проверяет фактический engine context. Внешний вызов и оба этапа обёрнуты в `pcall`, одноразовый guard выставляется до теста. Поэтому self-test не исполняется до появления NPC и не предшествует spawn/setup; обычные NPC проходят этот код только по Story ID фильтру. Безопасность новой точки запуска ещё должна быть подтверждена в оригинальном CoP.

Файл добавлен в установочный список как **gamedata/scripts/gpt_world.script**. Он не зарегистрирован в **modules.script** и не является NPC-схемой. Сам snapshot — только объективный контекст движка; в систему знаний он автоматически не записывается.

Публичный контракт будущего доменного API (имена предварительные):
- **get_catalog_levels()** / **get_catalog_entity(entity_id)** — read-only справочник уровней и сущностей;
- **get_catalog_smart_terrains(level_entity_id)** — read-only справочник 53 Smart Terrain/A-Life адресов;
- **get_companion_location_snapshot(companion_alife_id?)** — read-only источник объективного текущего местоположения; принимает известный A-Life ID или разрешает уникального спутника по Story ID;
- **record_claim(claim)** — добавляет явное утверждение с provenance/confidence и необязательным `level_id` для POI без каталожной записи; текущий backend ограничен памятью Lua-сессии, лимит 512 claims;
- **get_claims(subject_id, predicate)** — возвращает копии утверждений, не раскрывая внутреннюю таблицу;
- **get_known_places(filters)** — возвращает только сущности с положительным `known_place` claim; каталог сам по себе не открывает места;
- **record_observation(event)** — принимает только явно подтверждённое событие `place_observed` (с `level_id`, если место ещё не внесено в каталог) и создаёт claim со статусом `observed`;
- **get_companion_world_context(companion_alife_id?)** — возвращает раздельные поля `engine` (текущие факты X-Ray) и `knowledge` (только явные claims).
- **run_knowledge_api_self_test(companion_alife_id?, test_level_id_override?)** — диагностическая функция: проверяет public claims/observation API на временном изолированном хранилище и восстанавливает исходную таблицу и sequence ID даже после ошибки. При переданном synthetic `test_level_id_override` core-тест не зависит от A-Life snapshot; engine context проверяется отдельным вызовом после подтверждённого spawn/online. Не предназначена для игрового диалога.

У API должно быть явное разделение catalog и knowledge. Функция, возвращающая каталог, не должна использоваться LLM как перечень уже известных персонажу мест.

Модуль должен:
- принимать только данные спутника **gpt_companion_main**;
- не менять глобальные правила обычных NPC;
- не сканировать весь мир каждый тик;
- не хранить сырые указатели на игровые объекты в долговременной памяти;
- допускать отсутствие неизвестных/неподдерживаемых полей без падения;
- возвращать nil/пустой результат при отсутствии данных, а не подставлять выдуманное знание.

## 6. Сохранение и жизненный цикл

Знания принадлежат компаньону, а не игроку. Использование actor PSTOR как постоянного хранилища мира было бы лишь временным техническим обходом: уже сейчас actor PSTOR используется для потребностей спутника из-за online/offline особенностей, но семантически он принадлежит игроку.

У **sim_squad_scripted** уже есть собственные **STATE_Write/STATE_Read**, однако сейчас они сериализуют только четыре строковых поля: **current_target_id**, **respawn_point_id**, **respawn_point_prop_section** и **smart_id**. Расширение save-пакета нельзя делать без отдельного анализа размера/версии пакета и совместимости старых сохранений.

До реализации persistence adapter требуется:
1. проверить, где именно сохраняется A-Life squad и как size передаётся в STATE_Read;
2. определить безопасный формат версии и чтения старых save;
3. проверить, переживает ли состояние спутника online/offline, смерть и повторную загрузку;
4. ограничить размер хранилища и предусмотреть удаление/сжатие устаревших записей.

Не менять сериализацию companion squad в рамках первого шага 2.1. Сначала зафиксировать модель данных и найти совместимый backend. Не переносить знания в PSTOR игрока по умолчанию. Текущая реализация claims — ограниченный session-only прототип: она проверяет контракт и разделение слоёв, но не переживает перезапуск Lua/игры и не должна называться постоянной памятью.

## 7. Связь с будущей памятью и агентностью

Модель мира и эпизодическая память связаны, но не тождественны:
- эпизодическая память отвечает: «что со мной произошло?»;
- модель мира отвечает: «что я сейчас считаю известным о месте/человеке/объекте?»;
- источник/время/уверенность связывают оба слоя;
- выводы Character Core не должны превращать предположение в объективный факт;
- внешний LLM позже получит подготовленное представление только из слоя знаний, а не прямой доступ к полному состоянию движка.

## 8. План реализации

| Шаг | Результат | Критерий завершения |
|---|---|---|
| 2.1-A | Контракт модели данных и идентификаторов | Сущности, claims, provenance и границы слоёв описаны |
| 2.1-B | Аудит движковых источников CoP 1.6.02 | Источники Story ID, game vertex, level name, online/offline object и Smart Terrain статически просмотрены; lazy-load механизм проверен по engine source; retail runtime ещё не проверен |
| 2.1-C | Статический каталог уровней/Smart Terrain | Реализованы 5 engine level names и 53 Smart Terrain/A-Life адреса из указанных LTX-источников; полнота каталога для специальных/сторонних карт не заявляется; каталог не раскрывает знания автоматически |
| 2.1-D | Минимальное хранилище claims | API записи/чтения claims и confirmed observation реализованы; session-only backend, без save persistence |
| 2.1-E | Сохранение | Состояние переживает save/load и online/offline без потери и дубликатов |
| 2.1-F | Первые события открытия мест | Компаньон знает только текущую исходную область и то, что реально узнал |

После 2.1 можно переходить к объектам, услугам, группировкам, NPC и связям-маршрутам. Не следует начинать с маршрутизации или автономного исследования, пока персонаж не умеет надёжно хранить и различать уже известные места.

## 9. Проверка и ограничения

- Целевая среда — оригинальный Call of Pripyat 1.6.02; наличие метода в OpenXRay не доказывает его наличие в этой сборке.
- Статическая проверка исходников не равна тесту движка.
- Первая игровая проверка географического слоя должна быть возможна на текущем уровне, без обязательного перехода Затон → Юпитер → Припять.
- Когда вернёмся к тестированию потребностей/лечения, сначала добавим безопасную диагностику их фактических значений и причин перехода в wounded, чтобы не требовать от игрока угадывать пороги по ощущениям.
- Пока нет однозначного контракта сохранения, изменения существующих save-пакетов и игровых binder-цепочек откладываются.
- **gpt_world.script** подключён через ленивую загрузку глобального namespace при первом обращении из companion setup и добавлен в установочный список. Реальное срабатывание автозагрузки и строка [GPT_WORLD] ещё должны быть подтверждены в retail CoP.
- Read-only adapter и его API обёрнуты защитными pcall, но это не заменяет Lua-компиляцию или проверку в оригинальном X-Ray 1.6.02.
- Каталог Smart Terrain — статическая первая выборка из базовых start_position и simulation property sections. Неизвестные тестовые карты и сторонние моды автоматически не покрываются.
